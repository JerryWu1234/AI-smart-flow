# 从不可变 Git 证据直接派生 Publish，并移除 DeliveryBundle

本变更删除 DeliveryBundle、签名实现与 bundle CLI，把自动发布和恢复的输入收敛为当前 Candidate、同 Revision 的 `REVISION_RESULT` 与 Run Git object store，并增加 owning Host 驱动的人工目标确认。正常 v6 路径在 adapter capability、Project Publish lease 和全路径 expected-old preflight 通过后才持久化 `PREPARED`，人工确认也只在所有 target kind/hash/mode 精确匹配时合成 `manual-confirmation-v1` 的 `COMMITTED` 结果。主要问题集中在兼容路径：v5 recovery-blocked 状态迁移后仍可能保留普通重试，旧 macOS `/var` 路径也没有被规范化为当前 lexical Data Dir 相对形式。CLI/runtime/public exports 已移除 bundle/signing 行为，但顶层 README 仍宣称 doctor 检查 signing。

**Watch for:** **confirmed / S1** — v5 `PUBLISH_RECOVERY_BLOCKED` 的 `retry_publish` 会被迁移保留，并可能以新的 Git-derived operation identity 覆盖旧 attempt；**confirmed / S1** — 旧 macOS `/var`→`/private/var` objectDirectory 在 v6 cleanup 中会被判为越界并中断终态清理或 daemon 启动；**confirmed / S3** — README 仍暴露已删除的 signing capability。

**Verdict**: NEEDS_CHANGES

## High-level view

Publish source 不再由可变 worktree 或自包含交付包提供。`verifyRunArtifacts()` 验证 Manifest、Candidate、Review、Leader decision 与 snapshot chain，`gitPublishOperations()` 要求 Candidate 的 revision/result hash 精确绑定当前 `REVISION_RESULT`；默认 adapter 通过 `git cat-file blob`、Data Dir containment、SHA-256、size 和 object type 检查读取内容。

自动发布以 Candidate/Review/operations hash 生成稳定 operationId。Capability probe、Project Publish lease 和全部 target path 的 old kind/hash/mode preflight 都位于 `PREPARED` 之前，`SUBMITTED` 与逐路径结果继续进入 durable attempt/result journal；新产生的 PARTIAL/UNKNOWN/recovery-blocked 状态只提供 inspection/cancel。

人工流程只从 adapter unavailable 或零写入 preflight conflict 进入。Owning Host 的 `USER_INPUT_REQUIRED` 才投影 worktreePath，status/result、非 publish pause 和其他 Host 不取得该字段；每次确认写入 revision-bound request marker，mismatch 后的新 request 可重试，只有全目标精确匹配才提交。

Schema v6 通过 v4→v5→v6 preprocess 删除旧 Review claim 字段、`deliveryBundle` state ref 和 `export_bundle` action，而不删除旧 bundle 文件。**Confirmed:** 迁移没有收紧旧 blocked attempt 的动作，也没有修复旧版本在 macOS alias Data Dir 下留下的 canonical-relative objectDirectory。

## S1 / confirmed：v5 recovery-blocked attempt 可被普通重试换成新 identity

旧 v5 coordinator 对所有 publish pause 都持久化 `retry_publish | export_bundle | cancel`。当前 `migratePublishActions()` 只删除/转换 `export_bundle`，其余 action 原样保留；只要旧 Run 同时有 `deliveryBundle` 和 `publish`，迁移还写入 `legacyOperationIdentity` marker（`packages/state-store/src/schema.ts:300-341`）。因此合法 v5 `PUBLISH_RECOVERY_BLOCKED` 的 PREPARED/SUBMITTED/UNKNOWN/CONFLICT Run 在 v6 中仍可包含 `retry_publish`。

`ProjectRuntime.resume()` 按 durable `resumeActions` 放行后，`closedResumeRoute()` 允许 `PUBLISH_RECOVERY_BLOCKED → READY_TO_PUBLISH`（`apps/daemon/src/project-runtime.ts:239-247,671-674`）。PREPARED/SUBMITTED、blocked pause 或 `legacyOperationIdentity` 会跳过当前 Git-derived publish identity 校验（`apps/daemon/src/recovery-manager.ts:284-295`）。对于含 ADD/MODIFY 的旧 Bundle，旧 operation hash 绑定 `delivery-bundle/blobs/...`，新 hash 绑定 `git-object-store/blobs/<blobId>`，stable operationId 因而不同。`StateStorePublishAttemptStore.get()` 把不同 operationId 视为 attempt 不存在，`prepare()` 随后用新 PREPARED 覆盖 `run.publish`（`apps/daemon/src/publish-coordinator.ts:141-143,216-220`）。当 legacy lease 已释放或记录为 null 时，adapter 会再次运行，而不是保持 identity mismatch/PARTIAL/UNKNOWN blocked。

```text
v5 blocked attempt (old operationId, retry_publish allowed)
        │ schema v6 migration keeps retry_publish
        ▼
READY_TO_PUBLISH + legacyOperationIdentity
        │ Git blob refs produce a different operationsHash/operationId
        ▼
get(new operationId) = undefined
        └── PREPARED replaces old journal → adapter may run again
```

修复应同时收紧迁移和执行层：有 legacy `publish` 的 blocked/in-flight Run 必须迁为 `PUBLISH_RECOVERY_BLOCKED` 且只保留 `inspect_recovery | cancel`，`closedResumeRoute()` 不应允许 blocked retry，`PublishCoordinator.publish()` 也应拒绝在已有不同 identity 的 `run.publish` 上创建新 attempt。增加真实 v5 SQLite migration cases，覆盖 PREPARED、SUBMITTED、CONFLICT、PARTIAL/UNKNOWN、lease present/null 和 ADD/MODIFY operation。

现有迁移测试把一个带 SUBMITTED attempt 的 adapter-unavailable Run 断言为同时提供 `retry_publish` 与 `confirm_manual_publish`（`packages/state-store/src/schema.test.ts:118-157`）；后者又会被 runtime 的 `run.publish === undefined` 条件拒绝。该断言既未覆盖 blocked migration，也固化了一个对外可见但不可执行的 action set。

## S1 / confirmed：旧 macOS objectDirectory 无法通过 v6 cleanup containment

新 `initializeGitObjectStore()` 在 canonical path 初始化 bare repository、但返回 caller 请求的 lexical `/var/...` path（`packages/workspace/src/git-object-store.ts:26-38`），随后 Worker 将其相对化写入 state（`apps/daemon/src/worker-runner.ts:428-430`）。v4/v5 migration 只改 schema/action/ref，没有规范化 `gitWorkspace.objectDirectory`；该字段仍只要求非空字符串（`packages/state-store/src/schema.ts:41,347-371`）。

旧实现先 `realpath(runDataDirectory)`，所以 macOS `/var/folders/...` 下会返回 `/private/var/folders/.../git-object-store/objects`。以 lexical Project Data Dir 做 `relative()` 后，旧 state 保存类似 `../../../../private/var/.../objects`。本机确认 `/var` 的 realpath 为 `/private/var`；该值能通过 schema，但 `cleanupGitRunTemporaryState()` 以 lexical `relative(root,target)` 拒绝所有 `..` target（`packages/workspace/src/git-cleanup.ts:14-25,51-55`）。ProjectRuntime 在启动迁移后同步 cleanup 每个 terminal Run（`apps/daemon/src/project-runtime.ts:439-442`），所以一个旧 terminal Run 即可用 `GIT_CLEANUP_PATH_UNSAFE` 中止 daemon recovery；active Run 完成后的 cleanup 也会失败。

修复应在知道 `StateStore.dataDirectory` 的迁移层或 cleanup 边界同时比较 canonical root/target，在证明目标是同一 Run 的预期 `runs/<jobId>/git-object-store/objects` 后重写 state 为 portable relative path，不能简单放宽 `..` 检查。增加 Darwin alias 或通用 symlink-alias fixture，覆盖 v4/v5→v6、terminal startup cleanup、active completion cleanup、外部路径拒绝，并断言 legacy delivery file 仍存在。

## S3 / confirmed：公开 README 仍宣称 doctor 检查 signing

CLI 已删除 bundle verify/export，Doctor capability 现在只有 config、data-dir、sandbox、provider 和 apply-adapter，publish package 也不再导出签名 API。`README.md:16` 仍写着 `smartflow doctor --json` 会验证 “signing and publish capabilities”，会让安装者继续寻找已删除的 signing key/capability。删除 signing 表述，并让 README 与 apply-adapter/manual-confirmation 语义一致。

## 验证与未覆盖边界

验证通过：针对性 Vitest 66/66（schema/protocol/Git snapshot+cleanup/Host turn/publish CAS/crash lifecycle/publish safety）、root TypeScript typecheck、changed-source ESLint、`git diff --check main`，以及 flow visualizer 两个变更 JS 文件的 `node --check`。**Not tested / confirmed:** 仓库没有 `readGitBlob` 的负向 object-type/hash/size/outside-Data-Dir 测试，没有 `/var` alias migration/cleanup case，没有通过真实 `smartflow_resume`/Host replay 覆盖 mismatch 后新 request，也没有 StateStore-level v5 DB + legacy delivery file 保留测试；`vitest apps/flow-visualizer` 因无测试文件退出 1，语法检查通过。
