# SQLite StateStore、CAS mutation 与 daemon singleton 切换

本次改动把 Project state 和 audit events 从 `state.json`/`events.jsonl` 迁到 WAL 模式 SQLite，并用 `stateVersion` CAS 加进程内 mutation queue 取代每次 mutation 的 Project file lock。启动路径改为先获取 daemon singleton 再导入和恢复，Worker Candidate 则收敛到 v3 Candidate 加快照绑定，不再保存独立 patch/evidence Artifact。当前有两个直接阻断上线的问题：失败的第二实例会删除首实例 socket，legacy `state.json` 也没有被可靠退役；CAS 本身还没有覆盖原 Project lock 的跨进程串行化和 effect handoff 语义。

**Watch for:** **confirmed** — 第二个 daemon 的锁失败清理会让正在运行的 daemon 失联；**confirmed** — legacy `state.json` 可继续成为第二 authority，且无 import marker 时会被静默忽略；**confirmed** — 跨进程 CAS 冲突不会重放/重试，外部 effect 可被另一 writer 穿过；**confirmed** — 并发 `ProjectMutationSession.open()` 不形成抢占顺序；**confirmed** — 现有 crash tests 没有注入真实 WAL 生命周期。

**Verdict**: NEEDS_CHANGES

## High-level view

SQLite 的条件更新能阻止两个提交互相覆盖，但 authority handoff 仍有缺口：有 SQLite row 时读取立即返回，只有带 import marker 的 legacy 文件才检查 hash，而导入后原 `state.json` 仍留在原路径。由此，downgrade、旧 binary recovery 或后来出现的 legacy 文件仍可形成分叉。

Mutation 串行化现在来自模块内 `Map<dataDirectory, Promise>`，SQLite transaction 只覆盖最终 row update。单一 daemon module 内顺序成立，但独立进程、worker/module isolate 或其他 StateStore writer 会得到 CAS 失败而非等待、重读和幂等重放，`commit → prepareEffect → startEffect` 之间也没有数据库 barrier。

Singleton 提前到 recovery 前能约束当前 daemon，但新增失败清理没有区分“本实例已拥有 endpoint”和“获取锁前即失败”。Unix 上第二实例会 unlink 首实例仍在监听的 pathname，首实例继续持锁和运行却无法接受新连接。

## 失败的第二个 daemon 会摘掉首实例 socket

**S1 / confirmed.** `startSmartFlowDaemon()` 在 `server.acquireInstanceLock()` 抛出 `PROJECT_LOCKED` 后调用尚未拥有 lock、也从未 bind endpoint 的 `server.close()`；`LocalIpcServer.close()` 又无条件执行 `ignoreMissing(this.endpoint)`。先在目录 D 启动 daemon A，再经生产入口启动 daemon B，B 拿锁失败后 `D/daemon.sock` 消失；A 的进程、监听 fd 和 lock 仍在，但新连接得到 `ENOENT`。临时目录复现观察到 `secondAcquire="PROJECT_LOCKED"` 且 `socketExists=false`。

修复应记录 endpoint ownership，只在本实例成功 bind 后 unlink，或拆分“释放 instance lock”和“关闭已绑定 endpoint”。回归测试必须走 `startSmartFlowDaemon()` 的失败 catch，并在第二次启动失败后重新连接首实例；现有直接测试 `LocalIpcServer.start()` 不经过新增清理路径。

## legacy state.json 导入后仍是可写的第二 authority

**S1 / confirmed.** `readState()` 看到 SQLite row 就直接返回；`migrateState()` 仅在 `legacy_imports` 已有 marker 时比较 `state.json` hash。SQLite 先建立、legacy 文件后来出现时，迁移静默采用 SQLite；临时目录中 SQLite `stateVersion=0`、后来写入的合法 legacy `stateVersion=7`，`migrateState()` 仍返回 0。

从 legacy 导入成功后也没有 rename、删除或 tombstone 原文件，旧 binary 因而仍能把原路径当作恢复事实。Singleton 不能消除这一兼容窗口：旧版本在获取 daemon lock 前执行 recovery，可读取并推进残留 JSON；hash 又只在新 daemon 启动时检查，且 bytes 在 SQLite transaction 前读取，存在 TOCTOU 窗口。

迁移应在 singleton 下完成一次性 authority handoff：SQLite commit 后 durable rename legacy state 到 hash 命名归档或写入旧 binary 无法识别的 tombstone。SQLite row 与无对应 marker 的 `state.json` 并存时必须 fail closed；测试需覆盖 commit、legacy retirement、目录 fsync 间的 crash window及旧 recovery 路径。

## SQLite CAS 没有覆盖 build 到 effect-start 的互斥区间

**S2 / confirmed.** `ProjectMutationExecutor.mutationQueues` 只存在于单个 JavaScript module instance；`BEGIN IMMEDIATE` 只包住 `writeState()`，异步 `build()` 在 transaction 前，`prepareEffect()` 在 commit 后。两个隔离 writer 处理同一 requestId 时都会运行 build，胜者提交，败者收到 `STATE_VERSION_MISMATCH`，不会重读 winner receipt；不同 requestId 同样没有 bounded retry。

Effect handoff 也能被穿过：writer A 提交 `SUBMITTED` 后暂停在 `prepareEffect`，writer B 提交 cancel/phase change，A 随后仍调用 `startEffect()`。旧 Project lock 会把 B 挡到 effect 发起以后；当前测试通过只是因为两个 executor 共享同一 Map。

```text
writer A: read/build ─ commit SUBMITTED ─── prepareEffect ─ start apply
writer B:                         read ─ commit CANCELING ────────────
SQLite:                           两次提交都合法
```

若只有持有 installation singleton 的 daemon 才可写是永久不变量，应把 owner/epoch 写进数据库并让每次 mutation 校验。否则需保留跨进程 writer lease，或在 SQLite commit 中写 durable effect/outbox claim；CAS conflict 还要 bounded fresh-read retry，并先检查 receipt 以返回 canonical replay。对应测试必须使用 child process 或 worker isolate。

## ProjectMutationSession 的抢占不是原子 claim

**S2 / confirmed.** `ProjectMutationSession.open()` 先读 state 计算 `projectFence + 1`，再单独 `writeState()`。两个并发 open 读到同一 version/fence 时，一个成功，另一个直接得到 `STATE_VERSION_MISMATCH`；临时复现得到 fulfilled fence 1 和 rejected mismatch，而新增测试只覆盖顺序 open。

应使用条件更新加 `RETURNING project_fence, state_version` 原子分配 fence，或在 CAS 失败后 bounded 重读重试。`ownerId` 当前被完全丢弃；若并发 open 本来允许失败，则 API 描述和错误码应明确 contention，而不能承诺后一 session 抢占前者。

## 旧文件 checkpoint 无法证明 WAL crash safety

**S3 / confirmed.** `AFTER_TEMP_WRITE`、`AFTER_FILE_FSYNC` 都在 SQLite transaction 前，`AFTER_RENAME`、`AFTER_DIRECTORY_FSYNC` 都在 commit/close 后。`atomic-state.test.ts` 因而只验证 throw 位于 transaction 前或后，没有覆盖 WAL record、commit marker、checkpoint、`-wal`/`-shm` 遗留或 reopen replay。

应由子进程在可观测 barrier 前后退出/被终止，父进程保留 sidecar 并 reopen，验证 state、schema 和 import marker 只出现完整 old/new 组合；另用第二进程持有 write transaction 验证 500ms busy 与上层 retry。当前定向测试运行于 Node 25，CI 使用 Node 24，最低声明的 Node 22.19 `node:sqlite` API 尚未实际执行。
